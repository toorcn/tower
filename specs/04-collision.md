# 04. Collision and holds

## Goal

The server works out by itself when two agents are heading for the same code, tells both of them, and puts the lower-priority agent on hold for the contested files. After this phase the collision moment in the demo is real, not scripted.

## Depends on

Phases 1 and 3. Phase 2 should be merged so the result is visible, but this phase changes only the server.

## Build

### 1. Modes

`POST /v1/admin/reset` takes `{ mode: 'live' | 'scripted' }`, default `live`.

- `scripted`: `system` events posted to `/v1/events` are accepted and the server's own detection, holds and negotiation are off. This is what phase 2 used.
- `live`: `system` events from outside are rejected with a 400. The server produces them.

The simulator picks the mode by checking whether the scenario contains any `system` event. `GET /v1/state` reports the current mode.

### 2. Claims

Implement the claim rules from the overview as a pure module with tests:

- `file.read` adds `reading`, `file.edit` and the pre-edit hook add or upgrade to `editing`, a prediction adds `planned`.
- A new prediction for an agent replaces that agent's old `planned` claims and leaves its `editing` claims alone.
- Expiry as in the overview, checked on a 5 second timer.
- An agent leaving drops all its claims.

Claims are part of the snapshot.

### 3. Flight plan prediction

In live mode, when an `intent.declared` with empty `predictedFiles` arrives, from a prompt hook or from the simulator:

1. Ignore prompts under 4 words (follow-ups like "yes, continue").
2. Answer the hook straight away. Prediction runs in the background.
3. Ask the model for `{ summary, files }`: a summary of the task in at most 80 characters, and up to 8 paths from the file graph that the task will most likely change. Send only the prompt (already truncated) and the list of paths. Never send file contents.
4. Drop any returned path that is not in the graph.
5. Emit a second `intent.declared` with the summary as `text` and the files as `predictedFiles`, and set `planned` claims.

Fallback when there is no key, the call takes over 3 seconds, or the output does not parse: score each path by how many words from the prompt appear in its segments or file stem (after lowercasing and splitting camelCase), take the top 5 with a score above zero, and use the first 80 characters of the prompt as the summary.

### 4. Collision detection

After every claim change, apply the rule from the overview.

- New pair of agents: create a collision with a new `collisionId` and emit `collision.detected`.
- Same pair, new contested file: emit `collision.detected` again with the same `collisionId` and the full file list. The web app treats a repeat as an update.
- `summary` is one plain sentence, for example "Sarah's agent plans to change 2 files Hong's agent is editing."

**Priority on a file:** an `editing` claim outranks a `planned` claim. Between two claims of the same mode, the older one wins. The agent with priority keeps working. The other is held on that file.

### 5. Hold enforcement

`POST /v1/hook` for a pre-edit payload now answers according to the Holds table in the overview. Rules:

- The decision uses only in-memory state. No model call, no disk read. It must answer in under 300 ms.
- For Codex patches, check every file in the patch. If any is held, deny the whole patch and name the held files.
- A deny carries a reason the agent can act on:

  > Tower: `src/auth/session.ts` is held by Hong's agent (task: add refresh token rotation). A split is being negotiated. Do not edit this file or work around the hold. Carry on with files outside this list: [contested files].

- On each deny, emit `hold.applied` (at most once per agent and path every 10 seconds) and set that agent's status to `holding`.
- `TOWER_ENFORCE=warn` turns every deny into an allow with the same text as added context. `off` skips the check.

Build the exact response shapes from the fixtures and the hooks references, per tool. Unit test: given a state and a fixture payload, the response matches.

### 6. Mailbox

- `queueMail(agentId, kind, text)`.
- Any hook response for that agent that can carry added context (pre-tool, post-tool, prompt) includes all queued mail, then marks it delivered and emits `mail.delivered`. If the same response is also a deny, put the mail text in front of the deny reason.
- Stop hook: if the agent has undelivered mail, answer with the "keep going" shape and the mail as its reason. Do this once per mail. If the payload says a stop hook is already active, answer `{}` so we never loop.

On a new collision, queue:

- To the held agent: who it overlaps with, that agent's task, the contested files, and that they are on hold until a split is agreed.
- To the agent with priority: who is waiting, what they want to do, the contested files, and to keep going for now.

### 7. Tests

- Claims: upgrade, replace planned, expiry, leave.
- Collision rule: read plus edit does not collide, planned plus editing does, same pair joins one collision, a file covered by an accepted split does not collide.
- Priority: editing over planned, older over newer.
- Hook responses for allow, deny and warn, for both tools.
- Mailbox: delivered once, combined with a deny, stop-hook path, loop guard.
- Fallback prediction on the demo repo's file list returns `src/auth/session.ts` for a prompt about session expiry.

## Out of scope

- Negotiation and splits (phase 5). A collision stays open in this phase.
- Any new animation.
- Semantic overlap between tasks that touch different files.
- More than two agents in one collision.

## Done-check

1. `pnpm sim scenarios/demo-agents.jsonl` (no `system` events in the file): the server emits `collision.detected` between the two auth agents, and the map shows it. The third agent is not involved.
2. Unset `ANTHROPIC_API_KEY` and run it again: the collision still fires through the fallback.
3. Real run: in `demo-app-hong`, ask Claude Code to add refresh token rotation and wait for its first edit. In `demo-app-sarah`, ask Codex to add session expiry. Within a few seconds of the second prompt the map shows the collision, and the Codex session is refused when it tries to edit a contested file, with the Tower reason visible in its terminal.
4. In that run, the held agent carries on with other files and does not loop on the denied edit. If it loops, tune the reason text and report what you changed.
5. In that run, the first agent's terminal shows it received the "someone is waiting" note.
6. Set `TOWER_ENFORCE=warn` and repeat: no edit is refused, both agents get the warning.
7. Posting a `system` event to `/v1/events` in live mode returns 400.
8. `pnpm test` and `pnpm typecheck` pass.
